# Deploy CivicTrack with Render

This repository contains three different parts. Render runs the public Express API (`backend/`) and the private Python AI service (`ai-service/`). MongoDB Atlas stores application data. Cloudinary stores uploaded photos. The Expo app (`mobile/`) is built as an APK or app-store bundle after the API has a public HTTPS URL.

The root [`render.yaml`](render.yaml) creates **two paid Render services** in the Singapore region: a 512 MB API and a 2 GB AI service. Review Render's current prices and billing screen before clicking **Apply**. The AI models and PyTorch use substantial memory; 2 GB is a starting choice, not a measured guarantee. Increase the AI plan if its logs show an out-of-memory restart. There is no Render-hosted MongoDB in this Blueprint.

## 1. Prepare the accounts and repository

1. Create or sign in to [GitHub](https://github.com), [Render](https://dashboard.render.com), [MongoDB Atlas](https://cloud.mongodb.com), [Cloudinary](https://cloudinary.com), and [Expo](https://expo.dev).
2. Review the local Git changes, then commit and push the deployment files to the branch Render will use. Render builds from **GitHub**, not from files that exist only on your PC. Do not commit `.env` files or account credentials.
3. Confirm the four `.pt` weights under `ai-service/models/` exist on GitHub. They are required for AI predictions. Keep the repository private if you do not want to distribute the model weights.

## 2. Create the Atlas database

1. In Atlas, create a project and a MongoDB cluster. A free cluster can work for initial testing.
2. Open **Database Access**, create a database user with a long unique password, and grant it read/write access to the application database. This database user is separate from your Atlas login.
3. Open **Connect → Drivers**, select the Node.js driver, and copy the `mongodb+srv://...` URI. Replace its password placeholder and add a database name such as `/civictrack` before query parameters. URL-encode special characters in the password. Save the URI privately for the Render prompt.
4. Atlas **Network Access** will need the API service's Render outbound IP ranges. You can add those after the Render service exists in step 4. Its first deploy may fail database connection until then.

## 3. Prepare Cloudinary

In the Cloudinary console, get **Cloud name**, **API key**, and **API secret**. The secret goes only into Render's backend environment, never into Expo or Git. Production image upload now returns an error if Cloudinary is unavailable, instead of returning a photo URL that will disappear after a Render restart.

## 4. Create the Render services

1. Open [Render Dashboard](https://dashboard.render.com). Choose **New → Blueprint** and connect the GitHub repository containing this project. Select the branch with `render.yaml`.
2. Render will show `civictrack-ai` (private Python service) and `civictrack-api` (public Node web service). Check the **paid plans and estimated charges** before applying the Blueprint.
3. When prompted for environment variables, enter:

   | Variable | Value |
   | --- | --- |
   | `MONGODB_URI` | Atlas connection URI from step 2 |
   | `CLOUDINARY_CLOUD_NAME` | Cloudinary cloud name |
   | `CLOUDINARY_API_KEY` | Cloudinary API key |
   | `CLOUDINARY_API_SECRET` | Cloudinary API secret |

   `JWT_SECRET` is generated by Render. The Blueprint connects the API to the AI service on Render's private network. You do not need to enter `PORT`, `AI_SERVICE_URL`, or your home IP address.
4. Apply the Blueprint and watch **Deploys → Logs** for both services. AI startup can take longer while Python packages and four models load. The API will retry only on a new deploy if its initial database connection fails.
5. Open the `civictrack-api` service, then **Connect → Outbound**. Copy **all** listed IP ranges into Atlas **Network Access → Add IP Address**. Once Atlas accepts them, choose **Manual Deploy → Deploy latest commit** on the API service if it failed earlier.
6. Copy the API's external HTTPS URL from Render, for example `https://civictrack-api.onrender.com`. Check `https://YOUR-URL/health` in a browser. It should return JSON with `status: "OK"`. This confirms the API and database startup, not AI predictions.

Render's AI service is intentionally private and has no public `onrender.com` URL. The API uses the internal hostname supplied by the Blueprint. The four model files must load in the AI logs; then test an image through the app to check prediction end to end.

## 5. Point the Android app at Render and build it

The `preview` APK profile still uses the home-network IP for local testing. Use the new `render-apk` profile for an internet-connected APK. In PowerShell:

```powershell
cd mobile
npx eas-cli login
npx eas-cli env:set --name EXPO_PUBLIC_API_URL --value https://YOUR-API.onrender.com/api --environment production --visibility plaintext
npx eas-cli build -p android --profile render-apk
```

Replace `YOUR-API.onrender.com` with the actual Render hostname. You can also set that public URL in the Expo project's **Environment variables → production** dashboard. It is embedded in the APK, so it is not a secret. For a Play Store build, use `--profile production` after setting the same variable. Both release profiles fail configuration if the HTTPS `/api` URL is missing; they cannot silently package the old LAN address. If you change the URL later, build a new APK or publish a properly configured EAS update.

If you previously set a custom URL in the app's **Server Settings**, clear that override when testing the new APK; saved device settings can take precedence over the build URL.

## 6. Verify from outside your Wi-Fi

1. Open `https://YOUR-API.onrender.com/health` using mobile data.
2. Install the new `render-apk` build and test account registration and email/password sign-in.
3. Submit one complaint with a photo. Check the image URL returned by the API starts with `https://res.cloudinary.com/`, and reopen the complaint after restarting the API.
4. Test AI detection and verify the AI logs show the expected models loaded. Check both services' Render logs if it fails.
5. Google sign-in is separate: set `GOOGLE_CLIENT_ID` on the API and complete the Google OAuth client setup only if you intend to use that button. Email/password login works without it.

## Common problems

| Symptom | First check |
| --- | --- |
| API deploy exits before listening | Atlas URI, Atlas outbound IP allowlist, and API logs |
| `/health` works but login says network error | APK's `EXPO_PUBLIC_API_URL`, saved Server Settings override, and mobile data test |
| Photo upload returns an error | All three Cloudinary variables and API logs |
| AI service restarts or predictions fail | AI logs, loaded models, memory plan, and private `AI_SERVICE_HOSTPORT` variable |
| Build fails on missing API URL | Set the Expo `production` environment variable before building `render-apk` or `production` |

Do not run the demo database seed against a production Atlas database unless you have reviewed its users and passwords. This guide deploys the API and Android app; publishing Expo Web as a public site is a separate step and needs browser/CORS testing.
